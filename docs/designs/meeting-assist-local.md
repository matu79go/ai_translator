# 設計書: オンライン会議アシスト（ローカルLLM版）

- 作成: 2026-11-03
- 状態: **Phase 1・Phase 2 実装済み（2026-11-03、未コミット）**
- 関連: [CLAUDE.md](../../CLAUDE.md) / [dev-log](../dev-log.md)

## 1. 目的

英語のオンライン会議で、日本人ユーザーが次の2つを得られるようにする。

| 価値 | 中身 | 求める速さ |
|---|---|---|
| **リアルタイム翻訳** | 相手の発言を瞬時に日本語で理解する | 話している途中から、0.5秒以内 |
| **本音と返事の提案** | 相手が本当に求めているもの（本音）と、相手の心に刺さる返事を示す | 相手が話し終えた直後。本音を最優先する |

これまでの「意図の先行表示（intent_label / dialogue_act）」は**やめる**。翻訳が0.1秒で出始めるようになり、意図を先に出す価値が小さくなったため。代わりに「本音と返事の提案」を出す。

## 2. 決定事項（2026-11-03 の議論）

| 項目 | 決定 |
|---|---|
| LLM | GX10 の vLLM（Gemma 4 26B-A4B FP8、`http://<GX10_HOST>:8001/v1`）。同じ GPU を使う他のサービスと共用 |
| 翻訳の出力 | JSON をやめ、**訳文だけ**を流す |
| 意図推定 | **廃止** |
| 提案の言語 | 日本語のみ |
| 提案の方向性 | 賛成・反対などの型は決めない。相手の本音に応える自由な返事 |
| 提案のタイミング | **B案：相手の番が終わった時（沈黙1.5秒）**。文が確定するたびに裏で作り直しはしない（§5.3） |
| 双方向翻訳（自分が日本語で話す） | 今回は対象外 |
| 会議の音声の取り方 | まずは **A案：今のWebアプリで画面共有の音声を取る**（§4） |
| ASR | 当面は Deepgram のまま。Nemotron への置き換えは Phase 2 で検討（§8） |

## 3. 全体構成

```
┌─────────── Windows PC ───────────┐
│ Zoom / Teams / Meet（何でも）     │
│        │ スピーカーに出る音 = 相手の声だけ
│        ▼                          │
│ Chrome: Webアプリ                 │
│   getDisplayMedia（システム音声）  │
│   → 16kHz PCM                     │
└────────┬──────────────────────────┘
         │ WebSocket
         ▼
┌──── backend (FastAPI, WSL) ───────┐      ┌──── Deepgram（クラウド）────┐
│  音声 ──────────────────────────────────→│  nova-2 ストリーミング     │
│  ←────── 途中結果 / 確定結果 ─────────────│                            │
│                                    │      └────────────────────────────┘
│  ① 翻訳: 途中結果・確定結果のたび   │
│  ② 本音と提案: 沈黙1.5秒で1回       │──→ GX10 vLLM（Gemma 4 26B-A4B）
│     ①と②は同じモデルに同時に送る    │     同時に来たリクエストをまとめて処理
└────────────────────────────────────┘
```

### 同じモデルで①と②を同時に処理する仕組み

vLLM は、同時に来た複数のリクエストを**1回の計算でまとめて**進める（continuous batching）。モデルを2つ立ち上げる必要はなく、メモリも増えない。実測では、提案2本と同時に走らせても、翻訳の最初の文字までの時間は変わらず、全文の時間が約0.2秒伸びるだけだった（§7）。

## 4. 音声入力：会議の音声を取る（Phase 1 の範囲）

### 4.1 方針

`navigator.mediaDevices.getDisplayMedia()` で、画面共有と同じ仕組みで音声を取る。

- **Windows の Chrome / Edge**：「画面全体」を選んで「システム音声を共有」をオンにすると、PCで鳴っている音がすべて取れる。**Zoom や Teams のデスクトップ版でも使える**
- **どのOSでも**：「Chrome タブ」を選べば、そのタブの音声が取れる。Meet や Zoom のブラウザ版用
- 会議アプリは自分の声をスピーカーから鳴らさないので、**取れるのは相手の声だけ**になる。マイクで取っていたときの「自分の声も入る」問題がなくなる

### 4.2 変更点（`frontend/src/components/AudioRecorder.tsx`）

1. 入力ソースの切り替えを追加する：`マイク` / `会議の音声（画面・タブ共有）`
2. 「会議の音声」のときは次で取得する：
   ```ts
   const stream = await navigator.mediaDevices.getDisplayMedia({
     video: true,            // Chrome は video なしだと拒否するため必須
     audio: {
       echoCancellation: false,   // 相手の声を加工しない
       noiseSuppression: false,
       autoGainControl: false,
     },
     systemAudio: 'include',      // Chrome: システム音声の選択肢を出す
   } as DisplayMediaStreamOptions);
   stream.getVideoTracks().forEach(t => t.stop());   // 映像は使わないのですぐ止める
   if (stream.getAudioTracks().length === 0) {
     // 「音声を共有」のチェックが外れていた → 手順を案内するエラーを出す
   }
   ```
3. 以降の処理（`AudioContext` で16kHzにする → Int16 にして WebSocket で送る）は今のまま使う
4. 利用者がブラウザの「共有を停止」を押すと、音声トラックの `ended` イベントが来る。そのとき録音停止と同じ処理をする
5. バックエンドの変更は不要（受け取る音声の形式は同じ）

### 4.3 制約

- Mac の Chrome では、システム音声は取れない。タブの音声だけ取れる。今回は Windows が前提
- 毎回、共有する画面を選ぶ操作が必要になる。会議画面と翻訳画面を並べて見ることになる
- Phase 3 の常駐アプリ（§8）で解消する

## 5. LLM の処理

### 5.1 ① リアルタイム翻訳

- **呼ぶタイミング**：今と同じ。途中結果（`min_words` と debounce で間引く）と確定結果
- **出力**：訳文だけ。届いた分から `translation_partial` として何度も送り、画面の訳を上書きしていく
- **古い結果の破棄**：新しい途中結果のリクエストが出たら、古いリクエストの結果は画面に送らない（連番で判定）。確定結果は必ず送る
- **プロンプト**：
  ```
  You are a real-time simultaneous interpreter. Translate the English utterance into natural Japanese.
  - If the utterance is incomplete, still produce a natural Japanese sentence for what has been said so far.
  - Output ONLY the Japanese translation. One version only. No quotes, no notes, no alternatives.
  ```
  ユーザー側には、直前の発言3つを文脈として付ける（今と同じ）

### 5.2 ② 本音と返事の提案

- **呼ぶタイミング**：最後の確定結果から**1.5秒の沈黙**が続いた時に1回。今の `SummaryGenerator`（`backend/main.py` の沈黙検知 `_delayed_summary`）の仕組みをそのまま使い、会話サマリーをこれに置き換える
- **入力**：会議の最初からの相手の発言（長くなったら直近N文に絞る。Nは要調整）
- **出力**：短いJSONを、**本音 → 返事の順**に流して生成する。本音が出来た時点で画面に送る
  ```json
  {"need": "相手の本音（30字以内）", "ready": true, "replies": ["返事1（40字以内）", "返事2"]}
  ```
- **`ready=false`**（相手がまだ前置きの段階）のときは、提案を出さないか、薄く表示する
- **プロンプト**：
  ```
  あなたはオンライン会議で日本人ユーザーを支える会話アシスタントです。
  相手（英語話者）の発言の流れから、相手が本当に求めているもの（本音）を読み取ってください。
  - need: 相手の本音を日本語で1文、30字以内。表面の発言の言い換えではなく、裏にある欲求・懸念を書く
  - ready: 相手がまだ前置きの段階で本題が見えなければ false
  - replies: 本音に応える、相手の心に刺さる返事を2つ。ユーザーがそのまま言える自然な日本語の口語、各40字以内
  JSONのみ、この順で: {"need":"...","ready":true,"replies":["...","..."]}
  ```
- **制約**：A案では自分の声が入らないので、ユーザーが何と答えたかは文脈に入らない。Phase 3 でマイクを別に取れば解消する

### 5.3 「文ごとに裏で作り直す」をやめた理由

一番大事なのは最後の1文で、それを受けてから作り直すことになる。そのため、裏で先に作っておいても待ち時間は縮まなかった（§7）。出力を短くして流しながら表示する方が効果が大きい。

### 5.4 WebSocket メッセージ（バックエンド → フロント）

| type | 中身 | 送るタイミング |
|---|---|---|
| `transcript` | 今のまま | Deepgram の結果 |
| `translation_partial` | `translation`, `source_text` | 訳文が伸びるたび（途中結果・確定結果の両方） |
| `translation_final` | `translation`, `source_text` | 確定結果の訳が出来たとき（TTS もここで発火する） |
| `insight_partial` | `need` | 本音が出来た時点 |
| `insight` | `need`, `ready`, `replies[]` | 提案が全部出来たとき |

`intent_partial` / `intent` / `hints` / `summary` は、この画面では使わなくなる。既存の画面との関係は §9 を参照。

## 7. 測定結果（2026-11-03、GX10 Gemma 4 26B-A4B、テキストを流した計測で ASR は含まない）

### 翻訳

| プロンプト | 最初の文字 | 全文（話している途中） | 全文（文の確定時） |
|---|---|---|---|
| JSON の中に翻訳（今の速度重視プロンプト） | 翻訳フィールドまで約2.3秒 | 3.3秒 | 4.1秒 |
| **訳文だけ** | **約0.1秒** | **約0.4秒** | **約0.6秒** |
| 参考：以前のAPI（dev-log、ASR込み） | — | — | 平均 約2.1秒 |

### 本音と提案（4シナリオ×3回、相手の番が終わってから）

| 出力 | 本音 | 返事の1つ目 | 全部 |
|---|---|---|---|
| 長い版（要約・本音・返事3つ＋理由） | — | — | 中央値4.4秒、最大7.0秒 |
| **短い版（本音・返事2つ）** | **中央値0.55秒（最大0.66秒）** | 1.1秒 | 1.6秒 |

- 沈黙の検知に1.5秒かかるので、**相手が話し終えてから約2秒で本音が、約2.6秒で返事が出る**
- `ready` は前置きだけのとき `false`、本題が出ると `true` になり、正しく判定できた

|---|---|---|
| 翻訳だけ | 67ms | 469ms |

## 8. フェーズ

| Phase | 内容 | 音声の取り方 | ASR | LLM |
|---|---|---|---|---|
| **1（今回）** | 会議の音声で、翻訳と本音・提案を出す | 画面共有の音声（A案） | Deepgram | GX10 |
| 2 | 完全ローカル化 | 同上 | **Nemotron 3.5 ASR Streaming 0.6B を GX10 に置く** | GX10 |
| 3 | 実用版 | **Windows 常駐アプリ**（Electron / Tauri。WASAPI ループバックで相手、マイクで自分を別々に取る。最前面に字幕と提案のウィンドウを重ねる） | Phase 2 の結果次第 | GX10 |

### Phase 2：Nemotron ASR の評価計画

速さが問題になるとは限らない。Deepgram は音声を海外のサーバーと往復させているが、Nemotron は家の中の GX10 で動き、0.6B と小さいため。以下を同じ録音で比べて判断する。

1. **最初の途中結果が出るまでの時間**（音声の区切り 160 / 320 / 560ms ごと）
2. **英語の誤り率（WER）**：公式値は FLEURS で 8〜9%。Deepgram と同じ音声で比べる
3. **途中結果の出方**：Deepgram のように「途中の文字 → 確定」が来るか。翻訳を呼ぶタイミングの作りに影響する
4. **Gemma と GPU を共有したときの影響**：メモリは空き約24GBに収まる見込み

課題：GX10 に音声を受けるストリーミングサーバー（WebSocket）を新しく作る必要がある。`TranscriptionManager`（今は Deepgram 専用）を差し替えられる形にする。

| `frontend/src/hooks/useWebSocket.ts` | `translation_final` / `insight_partial` / `insight` の型 |

- 既存の画面（`ExperimentalApp`）と、他のモデルの動きは変えていない
- 接続先は環境変数 `GX10_BASE_URL` / `GX10_MODEL`。`GX10_BASE_URL` は未設定なら `http://<GX10_HOST>:8001/v1`（`GX10_HOST` は `.env` で指定） / `gemma4-26b-a4b`
- 会議の画面では TTS を使わない。システム音声を取っているので、読み上げた音声をまた拾って翻訳するループになるため

### 設計からの変更
- **沈黙タイマーの延長**：確定結果だけでタイマーをリセットすると、1文を言い終えるのに1.5秒以上かかった時点で、話している途中なのに本音が出てしまった。途中結果が来たときもタイマーを延長するようにした（`on_speech_activity`。`gx10` モードのときだけ）

### 通しテスト（Windows の音声合成で作った英語24秒の音声を、ブラウザと同じ形式で実時間で流した）
| 項目 | 結果 |
|---|---|
| ASR の確定結果 → 確定した訳 | 約0.4〜0.5秒（初回のみウォームアップで約2.5秒） |
| 話している途中の訳 | 確定結果より先に出る（例：6.45秒に途中の訳、6.61秒に ASR 確定） |
| 最後の ASR 確定結果 → 本音 | 約2.3秒（沈黙1.5秒＋生成約0.5秒＋α） |
| 最後の ASR 確定結果 → 返事2つ | 約4.2秒 |

### 分かった課題（未対応）
1. **相手の番の途中で本音が出ることがある**：文と文の間の間（ま）が1.5秒を超えると発火する。前置きの段階なら `ready=false` で薄く表示されるので実害は小さい。沈黙の閾値を2秒程度に延ばすか、設定可能にすることを検討
2. **生成中の本音が新しい発言で打ち切られる**：本音だけが出て返事が出ないまま残ることがある（画面は「考え中...」のまま）。次の番の終わりに上書きされる
3. **Deepgram が1文を途中で切って確定させる**と、その断片だけを訳すので訳がおかしくなる（例："if we already have a sort of works" → 「すでにいくらかの作業が進んでいるのであれば」）。`speech_final`（発話の終わり）まで断片をつなげてから確定訳を出す方式を検討
4. 実際の Zoom / Teams / Meet で、Windows の「システム音声を共有」を使った確認はまだ（ユーザーの手元での確認が必要）

### 修正（2026-11-03 午後、ユーザーの実地テストで発覚）
1. **確定の訳が作られず、訳が画面から消える**（主因）：`IntentEstimator.estimate()` の重複判定 `if text == self.last_text` が、直前の途中結果と同じ文の確定結果までスキップしていた。確定結果はスキップしないよう修正（全モード共通）
2. **断片をつなげる**（課題3の対応）：`gx10` モードでは、Deepgram の確定結果を `UtteranceEnd`（`utterance_end_ms=1000`、単語が1秒途切れた）までつなげ、全文で確定の訳を作る。話している途中は、つなげた文の途中の訳を出し続ける。40語を超えたら区切る。`UtteranceEnd` の後に確定結果が来た場合は、1.5秒後に区切る（保険）
   - Deepgram の `speech_final` は既定の10ms無音で立つため、区切りには使えなかった
   - 本音の沈黙タイマーは、区切った時点から0.5秒（`GX10_INSIGHT_SILENCE_MS`）。話が再開したらタイマーを取り消す
   - 通しテストで改善を確認：以前「すでにいくらかの作業が進んでいるのであれば」となっていた断片が、「正直なところ、すでに似たようなものが機能しているのに、なぜこれほど高い費用を支払わなければならないのかと、ディレクターから聞かれているんです。」に。最後の ASR 確定から確定の訳まで約1.9秒、本音まで約1.9秒
3. **同じ訳が繰り返されて見える**（2の副作用）：間を空けずに話す人だと1秒の間が来ず、断片が上限まで長くなり、途中の訳がその長い文を毎回最初から訳し直していた。Deepgram の `speech_final`（短い間）が来た時点で、つないだ文が `UTTERANCE_FLUSH_MIN_WORDS`（12語）以上なら区切るように変更。上限 `UTTERANCE_MAX_WORDS` は30語。どちらも環境変数で変えられる
   - 確定の訳を作るときは、保留中（debounce 中）の途中の訳のリクエストを取り消す（確定の訳の後に同じ文の途中の訳が出直すバグ）
   - 本音のタイマーは、本当に1秒途切れた時（`UtteranceEnd`）だけ始める。短い間で区切った時は履歴に足すだけ（文ごとに本音が出てしまったため）
   - 間なしで20秒話し続ける音声で確認：12語前後の文ごとに確定の訳（ASR 確定から約0.7〜1.0秒）、本音は話し終えた後に1回だけ
4. **訳が出ては消える**：途中の訳を1文字目から流しながら表示していたため、新しいリクエスト（0.3〜0.5秒ごと）のたびに行が1文字に戻っていた。**訳が出来上がってから送る**ように変更（途中の訳・確定の訳とも）。新しいリクエストが来ても古い訳は捨てず、すでに表示した訳より新しければ表示する（話し続けると何も出なくなるのを防ぐ）。画面側は、同じ文（原文の最初の3語が同じ）で訳が大きく短くなる更新は表示しない

### 検証方法（再発防止）
YouTube の面接動画（Behavioral Mock Interview、sjTxmq68RXU）の冒頭190秒を、ブラウザと同じ形式で実時間で流し、受信したメッセージを `MeetingApp` と同じ表示ロジックの Python シミュレーターに通して数える（scratchpad の `e2e_sim.py`）。

| 行が消える | — | 0 / 0 |
| 確定訳の重複 | — | 0 / 0 |

## 12. Phase 2 評価結果：Nemotron 3.5 ASR Streaming 0.6B（2026-11-03）

GX10 上で、LibriSpeech 9クリップ（269語、約117秒）を実時間で流して Deepgram と比較。詳細なレポートと手順は GX10 の `~/work/nemotron-asr/`（venv: `~/venvs/nemotron-asr`、Transformers 版）。

| エンジン / 区切り | 話し始め → 最初の途中結果 | 最後の単語 → 確定 | 単語の遅れ 中央値 / 上位10% | 誤り率（WER） |
|---|---|---|---|---|
| Deepgram nova-2 | 0.72〜0.79秒 | 0.22〜0.32秒 | 0.43〜0.48 / 0.92〜0.99秒 | 6.7〜7.1% |

- 途中結果は区切りごとに伸び、前の文字を書き換えない（Deepgram は途中結果の約10%で前の文字を書き換える）。大文字小文字と句読点付き

- **未検証**：実際の会議音声（システム音声、なまり、話者の重なり）。上の WER は条件の良い音声での最良値

| | EN2002a | EN2002b（重なり多） | EN2002c（重なり少） | 全体 WER | 単語の遅れ 中央値 / 上位10% |
|---|---|---|---|---|---|
| Deepgram nova-2 | 20.3% | 38.2% | 22.7% | **27.8%** | 0.64 / 1.39秒 |

## 13. Phase 2 設計：Nemotron ASR を Deepgram と切り替えて使う（2026-11-03、実装済み）

### 方針
- **Deepgram は残す**。画面のトグルで `Deepgram` / `Nemotron (GX10)` を切り替え、同じ会議で比べられるようにする
- GX10 の ASR サーバーが **Deepgram と同じ形式の合図**（途中結果・`is_final`・`speech_final`・`UtteranceEnd`）を返す。これで Phase 1 の断片つなぎ、本音のタイミング、表示ロジックをそのまま使える
- 区切りは 320ms（§12 の結果）。英語のみ（このモデルの設定）

```
ブラウザ ─音声→ backend ─┬─ Deepgram（クラウド）        … トグル: Deepgram
                         └─ GX10 :8092 Nemotron ASR    … トグル: Nemotron
                               └ 同じ形式の合図を返す → 以降の処理は共通
```

### 1. GX10 の ASR サーバー（新規）
- 場所：`~/work/nemotron-asr/server/asr_server.py`、venv は `~/venvs/nemotron-asr`（既存）。起動スクリプト `run_server.sh`（当面は手動起動。自動起動は後で検討）
- ポート：`8092`、`0.0.0.0` で待ち受け（LAN と Tailscale から届く）
- 接続ごとに1本の `model.generate()` を別スレッドで動かす。音声はキューで受け取り、320ms 分たまるごとに特徴量にして渡す（計測スクリプト `nemo_stream.py` の仕組みを、録音ファイルの代わりに受信した音声で動かす）
- 文字へは `processor.decode` で戻す（`tokenizer.decode` は "middle"→"midle" になるバグがある）。連続する空白は1つにまとめる
- **プロトコル**（WebSocket `ws://<GX10>:8092/ws`）
  - 受信：16kHz・モノラル・16bit PCM のバイナリ（今の Deepgram と同じ）、`{"type":"CloseStream"}`
  - 送信：
    - `{"type":"Results","transcript":"...","is_final":false,"speech_final":false}` … 途中結果。最後の単語が書きかけ（"apo"）なら、その手前の空白までを送る
    - `{"type":"Results","transcript":"...","is_final":true,"speech_final":true}` … 区切り（下記）。この区間の全文
    - `{"type":"UtteranceEnd"}` … 単語が1秒途切れた
- **区切りの判定**（Nemotron には確定の合図がないため、サーバーで判定する）
  - 新しい単語が出ないまま **300ms** たったら、その区間を確定（`is_final` と `speech_final` を両方 true）。Deepgram の短い間の確定に相当
  - 1区間が **25語** を超えたら、次に句読点（`.` `?` `!` `,`）が出た時点で確定（長すぎる区間を防ぐ）
  - 最後の単語から **1000ms** たったら `UtteranceEnd` を1回送る（Deepgram の `utterance_end_ms=1000` と同じ）
  - 時間は「新しい単語が出たか」で測る。音量による無音検出（VAD）は、まずは入れない。Nemotron は無音の間は単語を出さないので、これで足りる見込み。足りなければ後で追加する
- 同時接続：想定は1本。2本目も受け付けるが、GPU は共有になる

### 2. バックエンド（`backend/main.py`）
- `TranscriptionManager` に ASR の切り替えを追加：`asr_engine = "deepgram" | "nemotron"`
  - `start()`：Deepgram なら今のまま。Nemotron なら GX10 の ASR サーバーに WebSocket で接続し、受信用のタスクを起動する
  - 受信した `Results` は、今の `_on_transcript` に Deepgram の結果と同じ形で渡す（小さな変換用オブジェクトを使う）。`UtteranceEnd` は `_on_utterance_end` に渡す
  - `send_audio()` / `close()` は、選ばれている方に送る
- 新しい制御メッセージ `{"type":"set_asr","engine":"nemotron"}`：ASR の接続を張り直す（言語を切り替えるときと同じ流れ）。結果は `{"type":"asr_changed","engine":...}` で返す
- 環境変数 `NEMOTRON_ASR_URL`（既定 `ws://<GX10_HOST>:8092/ws`）
- GX10 につながらないときは `error` を返し、画面に表示する（自動で Deepgram に戻すことはしない。比べたいので、どちらで動いているかをはっきりさせる）
- 原文の言語が英語以外のときは Nemotron を選べない（エラーを返す）

### 3. 画面（`MeetingApp.tsx`）
- 見出しの横に、トグル `ASR: Deepgram | Nemotron (GX10)` を置く。接続時と切り替え時に `set_asr` を送る。録音中に切り替えてもよい（バックエンドが張り直す）
- 選択はブラウザに覚えさせる（`localStorage`。使えない環境でも動くようにする）
- 状態表示に、今どちらの ASR で動いているかを出す

### 4. 検証（渡す前に私の側で行う）
- 面接動画の190秒と、Windows の音声合成のテスト音声を、**両方の ASR で**通しで流し、表示シミュレーター（`e2e_sim.py`）で数える：行が縮む・消える・重複・抜け落ち、ASR の確定から確定の訳までの時間
- 2つの ASR で、画面に残る確定の訳を並べて比べる
- GX10 のメモリ使用量と、Gemma の応答速度への影響を確認する

### リスク
- GX10 の Wi-Fi が切れると ASR も止まる（Deepgram に切り替えれば続けられる）
- サーバーは手動起動。GX10 を再起動したら起動し直す必要がある
- 区切りの判定（300ms / 25語 / 1000ms）は推定値。検証で調整する

### 13.3 重要なリスク：英語らしくない発音を英語として書き起こせないことがある
Windows の音声合成で作った英語の音声の1つ（`turn.wav`）で、Nemotron が**1語も出力しなかった**（すべて `<pad>`）。言語を自動判定にすると、この音声を日本語と判定し、カタカナで書き起こした（「サンクスフォージョイニングアゲイン…」）。同じ音声を Deepgram は正しく書き起こした。別の合成音声（`cont.wav`）や、実際の人の声（面接動画、LibriSpeech）は正しく書き起こせた。
- **なまりの強い英語（日本人やアジアの話者を含む）で同じことが起きる可能性がある**。実際の会議で Deepgram と切り替えて確認すること
- 起きた場合は、画面に何も出なくなる。トグルで Deepgram に切り替えれば続けられる
