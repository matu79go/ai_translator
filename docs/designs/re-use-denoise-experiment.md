# 設計：NVIDIA RE-USE で雑音を消すと、どれだけきれいになるか（実験）

- 状態：**段 1・段 2・段 4 を実施済み**（2026-11-10）。結果は §9・§10。段 3 は未実施
- 目的：**「どれだけきれいになったか」を数字と耳で確かめる実験**。製品に組み込むかどうかは決めない（ユーザーの言葉：「今回はビジネスというよりもどれだけきれいになったかの実験ができればいい」）
- 経緯：nerve_runtime のセッションからの引き継ぎ。ai_translator には GX10 の Nemotron ASR と、会議音声（AMI）で誤り率を測った仕組みがあるので、こちらで行う

## 1. モデルについて分かっていること（2026-11-10、モデルカードと論文の要旨から）

| 項目 | 内容 |
|---|---|
| モデル | [nvidia/NVIDIA-NemotronLabs-RE-USE](https://huggingface.co/nvidia/NVIDIA-NemotronLabs-RE-USE)。多言語の「何でも直す」音声強調（Universal Speech Enhancement） |
| 大きさ | **9.6M パラメータ**（FP32、約 40MB の見込み） |
| 作り | 畳み込みの符号化・復号＋時間と周波数の両方向の Mamba（**双方向**、30 層） |
| 直せるもの | 雑音、残響、音割れ（クリッピング）、帯域の狭さ、コーデックの劣化、パケットの欠け、質の悪いマイク。**話者が重なったときは主な話者を残し、ほかを抑える** |
| 入出力 | モノラルの wav。8〜48kHz |
| 長さ | 学習は10秒未満の音声。30秒を超える音声は区切って処理する（`inference_chunk.sh`、`chunk_size_in_seconds` と `hop_length_portion` を指定） |
| 動かすのに要る物 | `mamba_ssm`（CUDA のビルド）。SEMamba のリポジトリに Docker の環境がある。確認されている GPU は Ampere（A100）、OS は Linux |
| ライセンス | OpenMDW-1.1。商用利用可（Nemotron ASR と同じ） |
| 公表値 | URGENT 2025 の公開テスト（正解あり）：PESQ 1.34→**2.57**、STOI 0.50→**0.78**、DNSMOS 1.84→**3.29**、文字の正解率（CAcc）81.3→**89.2%**。16kHz の分では PESQ 2.47、STOI 0.82 |
| 論文 | arXiv [2603.02641](https://arxiv.org/abs/2603.02641)（NeurIPS 2026）、[2606.25621](https://arxiv.org/abs/2606.25621)（"One Model, Many Latencies"、IEEE SLT 2026） |

### 引き継ぎの内容と違っていたところ・まだ分からないこと
- **VoiceBank-DEMAND の公表値は、モデルカードにも論文の要旨にもない**。論文の本文にあるかは未確認。なければ「NVIDIA の公表値と合うか」は、**URGENT 2025 の 16kHz の値（PESQ 2.47、STOI 0.82）と傾向が合うか**と、VoiceBank-DEMAND の一般的な値（下の §4.2）との比較に置き換える
- **GGUF 版と speech.cpp で動くかは確認できなかった**。検索で見つかった `NeMo-Speech.cpp`（Nemotron の音声モデル用の C++ の実行環境）は、文字起こし・話者分離・音声合成・翻訳だけで、雑音除去は載っていない。GGUF の道は、場所が分かるまで候補から外す
- **双方向のモデルなので、話しながら少しずつ処理する（ストリーミング）作りではない**。区切って処理すると、少なくとも区切りの長さ分は遅れる。2本目の論文は低遅延版の話のようだが、その重みが公開されているかは未確認
- GX10 は aarch64 で GPU は Blackwell（CUDA 13）。**`mamba_ssm` の CUDA 拡張がこの組み合わせでビルドできるかが、最大の不確かさ**（確認されているのは Ampere だけ）→ **ビルドできた**（§9.1）

## 2. 実験の全体（4 段）

最初は**段 1 と段 2 だけを小さく行う**。段 3・段 4 は、段 1・2 の結果を見てから決める。

```
            ┌─ 段1 耳で聞く        （前後を並べて聞く）
noisy.wav ─ RE-USE ─ enhanced.wav ─┼─ 段2 正解と比べる    （PESQ・STOI・SI-SDR、VoiceBank-DEMAND）
            （GX10 の GPU）         ├─ 段3 正解なしで採点  （DNSMOS、AMI と自分の録音）
                                    └─ 段4 音声認識への効き目（Nemotron の誤り率と遅れ、AMI）
```

- 雑音を消すのは GX10 で行う。採点（PESQ・STOI・SI-SDR）も GX10 で行った（当初は手元の PC の案だったが、PC には numpy もなく約 100MB を落とすことになるため。GX10 なら足すのは `pesq`・`pystoi`・`cython` の数 MB だけ）
- すべての段で、処理する前の音声と後の音声を同じ名前で2つのフォルダに置き、同じスクリプトで比べる

## 3. 段 1：耳で聞く

### 材料（合わせて約8本、各10〜30秒）
| 種類 | 本数 | 中身 |
|---|---|---|
| AMI の会議音声 | 2〜3 | 段 4 と同じ EN2002a/b/c から、重なりの多い所と少ない所 |
| VoiceBank-DEMAND の雑音入り | 2 | 段 2 のテストから、雑音の大きいもの |

### やり方

- 聞くときに見る点：雑音がどれだけ減ったか／声がこもる・金属的になる・語尾が切れるなどの副作用／**AMI で2人が重なった所で、片方の声が消えていないか**（モデルの仕様で、主な話者以外は抑えるため）

### 判定
数字では決めない。気づいた点を、良い点・悪い点に分けて書き残す（ブログの「聞いてみた」の章になる）。

## 4. 段 2：正解と比べる（VoiceBank-DEMAND）

### 4.1 材料
- VoiceBank-DEMAND（Valentini）の**テスト分だけ**：雑音入り 824 本と、雑音のない元の音声 824 本。話者2人、48kHz の wav。元は Edinburgh DataShare の `noisy_testset_wav.zip` と `clean_testset_wav.zip`（それぞれ約 150MB の見込み）
- 採点は **16kHz に落として**行う（この分野の慣習。PESQ の広帯域モードが 16kHz 用のため）。RE-USE への入力は、48kHz のままと 16kHz に落とした物の2通りを試す（どちらで良く出るかも結果のうち）

### 4.2 測る数字
| 指標 | 意味 | 範囲 | 雑音入りの一般的な値（16kHz、文献の値） |
|---|---|---|---|
| PESQ（広帯域） | 人が聞いた品質の推定 | −0.5〜4.5 | 約 1.97 |
| STOI | 聞き取りやすさ | 0〜1 | 約 0.92 |
| SI-SDR | 元の音声との波形の近さ（dB） | 大きいほど良い | 約 8.4 dB |
| 処理の速さ | 音声1秒あたりの処理時間（RTF）、GPU メモリ | — | — |

- 前後の差（処理後 − 処理前）を、824 本の平均と、ばらつき（1本ごとの差の分布）で出す
- 参考：VoiceBank-DEMAND で**学習した**専用モデルは PESQ 3.3〜3.6 まで出ている（SEMamba など）。RE-USE は VoiceBank-DEMAND で学習していない（学習データは DNS5・LibriTTS・**VCTK** など。VCTK は VoiceBank と同じ元の録音を含むので、話者が重なる可能性がある。結果に書き添える）
- 注意：SI-SDR は、波形をきれいに作り直す型のモデルでは、聞いた感じが良くても下がることがある（論文の「歪みと聞こえの良さの兼ね合い」の話）。PESQ・STOI と食い違っても失敗とは言わない

### 4.3 判定の基準（実験としての目安）
| 結果 | 読み方 |
|---|---|
| PESQ が +0.8 以上、STOI が下がらない | 「はっきりきれいになった」。URGENT 2025 での伸び（16kHz で約 +1）と同じ傾向 |
| PESQ が +0.3〜0.8 | 「効くが、学習していない種類の雑音では控えめ」 |
| PESQ が +0.3 未満、または STOI が 0.01 以上下がる | 「この音声には効かない」。入力の条件（48k / 16k、区切り方）を疑ってから結論にする |

## 5. 段 3：正解なしで採点（DNSMOS）

- 材料：段 1 の AMI と自分の録音（正解の音声がない物）。必要なら AMI の3会議×3分を全部
- 指標：DNSMOS（Microsoft の DNS Challenge の採点モデル、ONNX、CPU で動く）の **SIG**（声の質）・**BAK**（背景の静かさ）・**OVRL**（全体）。P.835 版を使う
- 段 2 の VoiceBank-DEMAND にもかけて、「DNSMOS の上がり方」と「PESQ の上がり方」が合っているかを見る（正解なしの採点がどれだけ当てになるかの確認）
- 判定：OVRL が +0.3 以上で「きれいになった」。BAK だけ上がって SIG が下がるときは「雑音と一緒に声も削った」と読む

## 6. 段 4：音声認識への効き目（Nemotron × AMI）

### 6.1 条件（README の 32.5% と同じ）
- AMI のテスト会議 EN2002a/b/c、開始300秒の位置から3分ずつ。個人マイクの音声を元の時刻どおりに重ねた物。正解は人手の文字起こし、言いよどみ（um, uh など）は両側から除く
- Nemotron 3.5 ASR Streaming 0.6B、320ms の区切り。GX10 の `~/work/nemotron-asr/` の計測スクリプトをそのまま使い、入力の wav だけ差し替える
- 比べる物：①そのまま（32.5% の再現）②RE-USE を通した物。**①も同じ日にもう一度測り、32.5% が再現するかを先に確かめる**

### 6.2 測る数字
- 誤り率（WER）：会議ごとと全体。**置換・脱落・挿入に分けて**数える（雑音除去で声が削られると「脱落」が増えるはず）
- 遅れ：RE-USE の処理時間（区切り1つあたり、ms）。区切りの長さ（例：2秒・5秒）ごとに、「区切りを待つ時間＋処理時間」を足した遅れを出す。今の Nemotron の単語の遅れ（中央値 0.29 秒）にどれだけ上乗せされるか
- 余力があれば：Deepgram（27.8%）にも同じ物を通す

### 6.3 先に分かっている心配
- **32.5% の音声は個人マイクを重ねた物なので、もともと雑音が少ない**。RE-USE が直すものがあまりなく、差が出にくい可能性が高い。差が出ないことも結果として書く
- 誤り率の主な原因は話者の重なり（EN2002b が 41.6% で最悪）。RE-USE は重なると主な話者以外を抑えるので、**ほかの話者の単語が消えて誤り率が上がる**かもしれない。会議ごとの脱落の数で確かめる
- 雑音除去でかえって音声認識の誤りが増えることは、よく知られている。上がっても下がっても意味のある結果として扱う
- 雑音の多い条件も見たいときは、AMI の**遠くのマイク（会議室の机の上のマイク、SDM）**の音声を追加の条件にする（このときは①の誤り率も新しく測る）

### 6.4 判定
| 結果 | 読み方 |
|---|---|
| 3会議すべてで WER が1ポイント以上下がる | 「会議の音声認識に効く」 |
| 差が ±1 ポイント以内、または会議によって上下が分かれる | 「この音声では差がない」 |
| WER が上がる | 「雑音除去が音声認識を邪魔する」。置換・脱落・挿入のどれが増えたかを書く |
| 遅れ | 単語の遅れの中央値が +0.5 秒を超えるなら、今の作り（話している途中に訳を出す）には組み込めない、と書く |

## 7. GX10 に入れる物（**ユーザーの OK をもらってから入れる**）

### 7.1 使う前の確認（毎回）
```bash
ssh gx10 'ps aux --sort=-%cpu | head -15; nvidia-smi'
```
GPU を他のプロジェクトが使っていたら、ユーザーに聞いてから始める。

### 7.2 入れる物の一覧
| # | 物 | 場所 | 大きさ（見込み） | 備考 |
|---|---|---|---|---|
| 1 | 新しい venv | `~/venvs/re-use`（`~/venvs/nemotron-asr` とは別） | 数 GB（PyTorch を含む） | PyTorch は `nemotron-asr` と同じ版（2.13、CUDA 13）を入れる |
| 2 | `mamba_ssm`（と、必要なら `causal-conv1d`）を**ソースからビルド** | 上の venv の中 | — | aarch64 + Blackwell では配布のビルド済みの物がない見込み。ビルドに数十分かかることがある。版は SEMamba のリポジトリに合わせる（要確認） |
| 3 | RE-USE のリポジトリ一式（重み・`inference.sh` など） | `~/work/re-use/model/` | 約 40MB＋スクリプト | `huggingface-cli download nvidia/NVIDIA-NemotronLabs-RE-USE` |
| 4 | VoiceBank-DEMAND のテスト分 | `~/work/re-use/data/vbd/` | 約 300MB | 雑音入り＋元の音声の zip 2つ |
| 5 | `resampy` | venv | 小 | 帯域を広げる機能を使うときだけ |

- **ダウンロードは速度を 1MB/秒に制限する**：`curl --limit-rate 1M -L -O <URL>`。Hugging Face からは、ファイルの URL を `curl --limit-rate 1M` で1つずつ落とす（`huggingface-cli` には速度の制限がないため）。合わせて約 350MB なので、約6分
- PyTorch などの pip のダウンロードも大きい。pip には速度の制限がないので、**`nemotron-asr` の venv の PyTorch を `--system-site-packages` ではなく、wheel のキャッシュから入れられるか**を先に見る。無理なら pip の前にユーザーに相談する（`trickle -d 1024 pip install ...` で制限する案）
- Docker（SEMamba の環境）は使わない案を第一にする。Docker のイメージは数 GB あり、aarch64 版があるかも分からないため

### 7.3 ビルドできなかったときの次の手
1. `mamba_ssm` の純粋な PyTorch の実装（`selective_scan_ref`）で動かす。遅いが、段 1・2 の「きれいになったか」は測れる（段 4 の遅れは測れない）
2. 手元の PC（RTX 3060、6GB）で動かす。9.6M なので GPU メモリは足りる見込み。ただし WSL で `mamba_ssm` をビルドすることになる
3. どちらも駄目なら、GGUF 版の場所を改めて探す

## 9. 結果（段 1・段 2、2026-11-10）

### 9.1 動かすまで
- 入れた物：venv `~/venvs/re-use`、`mamba_ssm` 2.3.2.post1（ソースからビルド、sm_121 だけ、`MAX_JOBS=4` で約 5 分）、`einops`・`ninja`・`wheel`・`cython`・`pesq` 0.0.4・`pystoi` 0.4.1、モデル一式（`~/work/re-use/model/`、38.6MB）、VoiceBank-DEMAND のテスト分（`~/work/re-use/data/vbd/`、zip で 325MB、展開後 693MB）。ダウンロードはすべて `curl --limit-rate 1M`
- **PyTorch は新しく落とさなかった**。`~/venvs/re-use` の site-packages に `.pth` を1つ置き、`~/venvs/nemotron-asr` の torch 2.13（cu130）・numpy・scipy・librosa・soundfile を**読み取りだけで**使う（nemotron-asr の venv は変えていない）。新しく入れる物は `--no-deps --no-index` で、落とした wheel からだけ入れる
- `mamba_ssm` 2.3.2 の `setup.py` は CUDA 13 と sm_121 に対応していた。causal-conv1d は不要（RE-USE の `Mamba` は、無ければ普通の畳み込みで動く）
- NVIDIA の `inference.py` は torchaudio を使うが、nemotron-asr の venv に torchaudio がないので、soundfile で読み書きする `experiments/re-use/enhance.py` を書いた（処理は同じ。1本ごとの処理時間を記録する）
- Gemma の vLLM は止めずに済んだ（RE-USE の GPU メモリは 16kHz で約 1.9GB、48kHz で最大 5.6GB）
- つまずき：librosa の `kaiser_best` は resampy が要る → `soxr_hq` に変えた

### 9.2 段 2：VoiceBank-DEMAND（824 本、16kHz で採点）
| | PESQ | STOI | SI-SDR | PESQ が下がった本数 |
|---|---|---|---|---|
| 処理する前 | 1.967 | 0.921 | 8.45 dB | — |
| RE-USE（48kHz のまま入力） | **3.228（+1.26）** | **0.962（+0.041）** | **19.22 dB（+10.8）** | 14 / 824 |
| RE-USE（16kHz に落として入力） | 3.087（+1.12） | 0.960（+0.039） | 19.23 dB（+10.8） | 34 / 824 |

- 処理する前の値は文献の値（1.97 / 0.92 / 8.4）と一致した。採点の仕組みは正しい
- **判定（§4.3）：「はっきりきれいになった」**。PESQ +1.26 は URGENT 2025 の 16kHz での伸び（約 +1）と同じ傾向。STOI も 95% の本で上がった
- VoiceBank-DEMAND で学習していないのに、PESQ 3.23 は VoiceBank-DEMAND で学習した専用モデル（3.3〜3.6）に近い。ただし学習データの VCTK に同じ話者が入っている可能性がある
- 48kHz のまま入れた方が良い（PESQ で +0.14）。帯域が広い方が情報が多いため
- 悪くなる例もある：**もともときれいな音声は悪くなることがある**（p257_083：PESQ 4.02 → 2.10）。STOI が大きく下がった例（p257_337：0.913 → 0.812）もある。聞き比べのページに入れた
- SI-SDR も大きく上がった（§4.2 で心配した「波形が離れる」ことは、平均では起きていない）

### 9.3 速さ（GX10、vLLM と同居。計測中、vLLM はほぼ空き）
| 条件 | 処理時間 ÷ 音声の長さ（RTF） | GPU メモリ（最大） |
|---|---|---|
| VoiceBank-DEMAND、16kHz、1本まるごと | 0.13（実時間の約 8 倍の速さ） | 1.9 GB |
| VoiceBank-DEMAND、48kHz、1本まるごと | 0.42 | 5.6 GB |
| AMI 3 分 × 3、16kHz、5 秒ずつ半分重ねて区切る | 0.25（区切り 1 つ約 0.6 秒） | 1.1 GB |

- 9.6M パラメータの割に速くない。周波数方向の Mamba を、時間の刻みの数だけ並べて計算するため（`b*t` 本の系列）

## 11. 雑音が消えたことを示す数字（雑音を大きくした音声、2026-11-10）

ユーザーの判断：「雑音を 6 倍にした聞き比べで、雑音除去ができていることは十分示せる。それを数字でも示したい」。用途の結論は「雑音のない音声の翻訳には意味がない。役に立つのは、雑音の大きい録音をあとから聞きやすくする使い方」。段 4 の続き（雑音の多い会議での文字起こし）は行わない。

`experiments/re-use/noise_floor.py`、結果は `results/noise_floor_hard.json`。正解の音声があるので、次の 2 つを出した。
- **SNR**：声が残った雑音より何 dB 大きいか。処理前は「雑音入り − 正解」、処理後は「出力（音量を正解に合わせた物）− 正解」を雑音とする
- **話していない間の音量**：正解の音声で一番静かな 20% の区間（20ms 単位）の音量（dBFS）

| 音声 | SNR（前 → 後） | 話していない間の音量（前 → 後） | 正解の音声の同じ区間 |
|---|---|---|---|
| p232_022（男性）・元のまま | +7.0 → **+18.8 dB** | −32.9 → **−51.2 dBFS** | −49.1 |
| p232_022・雑音 3 倍 | −2.5 → **+14.7 dB** | −23.5 → **−51.5 dBFS** | −49.1 |
| p232_022・雑音 6 倍 | −8.6 → **+11.9 dB** | −19.0 → **−52.8 dBFS** | −50.7 |
| p257_003（女性）・元のまま | +7.0 → **+18.1 dB** | −29.7 → **−51.1 dBFS** | −44.5 |
| p257_003・雑音 3 倍 | −2.5 → **+15.7 dB** | −20.3 → **−51.1 dBFS** | −44.5 |
| p257_003・雑音 6 倍 | −8.6 → **+13.7 dB** | −14.3 → **−49.8 dBFS** | −44.5 |

- 雑音 6 倍では、雑音の方が声より 8.6dB 大きかったのが、処理後は声の方が 12〜14dB 大きくなった（約 21dB の改善）
- 話していない間の音量は 34〜35dB 下がった（音の強さで約 2,500 分の 1、振幅で約 50 分の 1）。**処理後は、正解の音声（元の録音）より静か**。元の録音に入っていた部屋の小さな雑音まで消している
- 雑音が大きくなるほど処理後の SNR は少し下がる（18.8 → 14.7 → 11.9）が、話していない間の静かさは雑音の大きさによらずほぼ同じ（約 −51dBFS）
- 注意：つまずき。最初は処理前の音声も正解に音量を合わせて計算し、SNR が 0.6dB と出た（雑音の分だけ音量が小さく直されるため）。処理前は「正解＋雑音」そのものなので、音量は合わせない
